# Scheme Two: S-Function gateway to eLSD_Lib

This folder is a working prototype of **Scheme Two**: Simulink calls BSW
functions through C S-Functions generated by the Legacy Code Tool.

Scheme One (hand-written adapter outside the model) remains the recommended
integration path. Scheme Two is provided so the approach can be evaluated on
R2020b with the current headers.

## Why a flat wrapper still exists

`eLSD_Lib_Com_GetRx*` / `SetTx*` take **pointers to nested structs**. Simulink
ports cannot carry those structs directly. The S-Functions therefore call a
thin C layer (`eLSD_Sfun_FlatApi.c`) that:

1. Declares local snapshot structs.
2. Calls the real BSW functions.
3. Packs or unpacks the ASW-relevant fields into `single` vectors of widths
   40 (RX), 16 (TX) and 4 (motor). The field order matches `RxBus` / `TxBus` /
   `MotorCmdBus` in the parent Scheme One script.

So Scheme Two removes the **external** adapter file, but does **not** remove
the struct-to-signal mapping work. That mapping simply moves into the
S-Function sources that ship with the model.

## Layout

| Path | Role |
|---|---|
| `include/eLSD_Sfun_FlatApi.h` | Flat API used by the S-Functions |
| `src/eLSD_Sfun_FlatApi.c` | Get/Set packing (links against real BSW or stub) |
| `stub/eLSD_Lib_stub.c` | Host stub of `eLSD_Lib` for MEX / MIL |
| `build_sfun_eLSD_Scheme2.m` | Legacy Code Tool generate + mex |
| `build_VTC_Scheme2_R2020b.m` | Builds loopback and ASW Scheme Two models |
| `generated/` | S-Function sources and MEX (created at build time) |

## Build (MATLAB R2020b)

```matlab
cd('.../20260922更新/simulink/scheme2')
mex -setup C          % once
build_sfun_eLSD_Scheme2
```

Then, for the models:

```matlab
% Optional but needed for VTC_ASW_Scheme2_R2020b:
cd('..')
build_VTC_TorqueVectoring_R2020b
cd('scheme2')
build_VTC_Scheme2_R2020b
```

### Models produced

1. **`VTC_Scheme2_Loopback_R2020b.slx`**
   - `StubInjectRx` -> `GetAswRx` (sync wire enforces order)
   - `SetAswTxMot` + `StubReadTxMot` for TX/motor readback
   - No controller. Use to verify MEX linkage and field packing.

2. **`VTC_ASW_Scheme2_R2020b.slx`** (requires parent ASW)
   - Root inputs: `ExtInBus`, `Sync`
   - `GetAswRx` -> `RxBus` -> Model Reference `VTC_ASW_R2020b`
   - ASW `TxBus` / `MotorCmdBus` -> `SetAswTxMot`
   - Root also logs the buses

### MIL harness note

On the desktop the stub has no CAN. The harness (or a test script) must drive
`sfun_eLSD_StubInjectRx` with the flat RX vector and feed its sync output into
`GetAswRx`. On the target, delete the Stub* blocks, wire `Sync` to Constant 1,
and link the vendor `eLSD_Lib` instead of `eLSD_Lib_stub.c`.

## Target ERT checklist

- Keep `sfun_eLSD_GetAswRx` and `sfun_eLSD_SetAswTxMot`.
- Remove `StubInjectRx` / `StubReadTxMot` from the model.
- In Code Generation > Custom Code (or `coder.updateBuildInfo`):
  - Include path: folder with `eLSD_Lib.h`
  - Source / library: vendor `eLSD_Lib` (not the stub)
  - Still compile `eLSD_Sfun_FlatApi.c`
- Call the generated model step **only** from the customer 5 ms callback.
  Get/Set are not allowed outside that context per the header.

## Limits (unchanged from the analysis note)

- Host simulation needs the stub; stub behaviour can differ from the ECU library.
- A BSW interface change forces FlatApi, S-Function rebuild and model updates.
- ELD1 checksum is still a placeholder field (value from ASW / adapter policy).
- Friction and clutch temperature remain outside CAN (`ExtInBus`).
